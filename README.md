## 作りたいもの

Slay the Spire 2で、Actごとのエンシェントとボスを指定／Ban／候補制限し、アセンション効果を個別にON/OFFできるMOD。例えば「A1はOFF、A2はON」を可能にする。

- BaseLib・RitsuLib・ModConfigなど、別MODへの依存なし。ゲーム標準ローダーと同梱Harmonyを使う。
- 最初からマルチ対応を前提にする。ホストが設定を編集し、ゲストにも同じ設定を適用する。
- 初版は全員が同じSelectMODを導入する前提。ホストだけに入れて動く仕様にはしない。
- セーブ再開でも、そのランを始めたときの設定と確定済みの出現結果を使う。

「SelectMOD」は作業名。DLL名・MOD ID・バージョンは実装開始時に決める。

## まず採る設計案

初版の入口は標準のカスタムランを第一候補にする。通常ランやデイリーへの対応は追加検討。設定・保存・同期には標準のModifierModel経路を優先し、足りない保証だけ追加する。現行DLLで確認するまでは、標準経路だけで同期が完成するとは扱わない。

設定は「各PCの次回用の既定値」「ホストがロビーで編集中の値」「ラン開始時に固定した値」に分ける。ゲストの既定値は書き換えない。開始後は固定したラン設定だけを使う。

設定や候補が食い違った場合は、理由を出して開始・進行を止める。互換チェックやState Divergence検知を無効化して進める方法は採らない。詳細はDESIGN_AND_LESSONS.mdを参照。

## ビルド・導入

**今はSelectMODをビルド・導入するコマンドはない。** ルートにcsprojやscripts/Setup.ps1は未作成なので、参考MODのスクリプトをSelectMOD用として実行しない。

実装時は次の構成を用意する予定。

1. 手元の正規ゲーム環境でruntimeconfigと参照DLLを確認し、対応する.NET SDKを決める。前作は.NET 9だったが、SelectMODの対象版は未確定。
2. ゲームDLLの場所を外部指定できるcsprojを用意する。sts2.dll・0Harmony.dll・GodotSharp.dllは参照のみで、Gitや成果物に同梱しない。
3. Windowsではscripts/Setup.ps1をセットアップ・更新の入口にする。前提確認→テスト→実DLLビルド→設定準備→ステージング→導入をまとめる。失敗時は既存の導入を維持する。
4. パスはGit対象外のlocal/paths.txtに保存する。上からゲームルート、ユーザーデータルート、SelectMOD設定ディレクトリの3行。初回作成後は編集内容を保持する。
5. Cloudではゲーム不要のルール検証・保存データ契約・同期状態のテストを行い、実DLLビルドと実機試験を別に記録する。

スクリプト完成時に、この節を作業ディレクトリ付きのコピー可能なコマンドへ更新する。診断は読み取り専用の出力スクリプトを用意し、local/配下のUTF-8テキストで受け渡す。

### PowerShellで権限エラーが出たとき

実装後も、原因ごとに対処する。「スクリプトの実行が無効」は実行ポリシー、「署名されていない」は取得元のブロック、導入先への「アクセス拒否」は書き込み権限、「使用中」はファイルのロックを確認する。すべてを実行ポリシーの問題として扱わない。

WindowsのPowerShellで現在のポリシーを確認する（作業フォルダは任意）。

```powershell
Get-ExecutionPolicy -List
```

信頼できるスクリプトに限り、そのプロセスだけのRemoteSignedや、該当ファイルだけのUnblock-Fileを検討する。組織のMachinePolicy/UserPolicyは上書きしない。書き込み拒否で必要な場合のみ同じWindowsアカウントで昇格し、使用中ならゲームを通常終了する。
